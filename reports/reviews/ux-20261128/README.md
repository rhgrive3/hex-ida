# 使い心地と自動機能のレビュー（2026-11-28）

対象: `main` の `4bcb45b`（このレビュー中に入れた修正 `e649289` を含む）。
試したバイナリ: 本当の対象である iOS ゲームの Mach-O（`tests/large-fixtures.json` の TsumTsum、44.3 MB、153,492 関数）。
方法: Chromium（Playwright、`ja-JP`、1366×900）で、人と同じようにボタンを押して試しました。画面写真はこのフォルダにあります。

バグの修正は別のエージェントが担当しています。このレビューは**改善点**が中心です。ただし、使えなくなるバグを 1 つ見つけたので、それはここで直しました（4 章）。

## 1. 結論

- **初めて使う人向けの作りは、とても良いです。** 日本語の説明、「HP・体力」のような目的のボタン、作業の自動保存と復元。IDA にない強みです。
- **でも、目的の答えまでの最後の一歩が弱いです。**
  - 候補の名前が `sub_...` のままです。
  - 候補を選んだ理由（どの文字列か）が見えません。
  - 候補を開くと、読みにくい疑似 C が出ます。
- **自動で動いてほしいことが、手で押すまで動きません。** 名前の復元、全体の地図（概要）がそうです。動いても、大きいファイルでは遅いです。

## 3. 良い点（残すもの）

1. 1 行ごとの日本語の説明。初心者にとって、IDA よりずっと分かりやすいです。
2. 目的のボタン（HP、攻撃力、課金…）。何をしたいかから始められます。
3. 作業の自動保存と復元。同じファイルを開き直すと、名前や差分が戻ります。
4. 開くのが速いです（44 MB で約 5 秒）。
5. 処理を途中で止める「キャンセル」と、今の段階の表示（「呼び出しと参照を索引しています…」など）があります。
6. 関数の画面の「次に見る」の案内（疑似 C、フロー、呼び出し、根拠、実行）が分かりやすいです。

## 4. 使えなくなるバグ（このレビューで修正済み）

- 内容: 「概要を更新する」と「自動解析を実行する」が、本物のバイナリで必ず失敗しました。`解析に失敗しました: Cannot mix BigInt and other types`。
- 原因: `js/rank.js:141` が、`functionsReferencing` の第 2 引数（BigInt が必要）に Number を渡していました。ほかの 6 か所の呼び出しは、どれも `BigInt(...)` にしています。暗号の定数（AES の S-Box など）が見つかったときだけ、この道を通ります。
- 修正: `BigInt(bytes)` にしました。`tests/crypto-entropy-wasm.test.mjs` の偽の関数が、引数の型を確かめるようにしました。直す前はテストが失敗し、直した後は通ります（8/8）。commit は `e649289` です。
- まだやっていないこと: 正式な全体ゲート（`npm run check`）は実行していません。

## 5. 改善点（効く順）

### 5.1 開いたらすぐ、自動で全体を解析する（いちばん大事）

- 今の状態:
  - 開いた直後は、名前のある関数が 0 個です。
  - ObjC の名前（3,230 クラスから 38,395 関数）は、最初に「調べる」を押したときに初めて付きます。
  - 全体の地図（概要）は、ボタンを押すまで作りません。押すと 30 分以上かかります。
- IDA の場合: 開くとすぐ、裏で自動解析が始まります。名前、参照、型がどんどん増えていきます。
- 提案:
  1. 開いたらすぐ、裏（Worker）で段階的に解析します。順番は、ObjC/Swift の名前 → 文字列の参照 → 呼び出しグラフ → 目的ごとの候補です。
  2. 画面の下に進み具合（例: 「名前 38,395 / 153,492」）を出します。
  3. 終わった段階から画面に反映します。
  4. 結果は、今ある差分の保存と同じ所に保存します。2 回目に開いたときは、すぐ出します。

### 5.2 ライブラリ関数に自動で名前を付ける（シグネチャ）

- 今の状態: 153,492 関数のうち、約 75% が `sub_...` のままです。同梱のシグネチャは ARM64 では `elf_arm_64_android-ndk` だけです（`third_party/rizin-sigdb/`）。
- このアプリは cocos2d-x（`CDAudioManager` など）、Google Mobile Ads（`GAD...`）、Adjust などを中に持っています。ゲームでよく使うライブラリは決まっています。
- 提案: iOS arm64 向けのシグネチャを作ります。対象は cocos2d-x、Unity IL2CPP ランタイム、OpenSSL、zlib、libpng、protobuf、Firebase などです。仕組み（`js/analysis/signature/`、`hexsig_engine.cpp`）はもうあります。足りないのはデータだけです。候補の名前が `sub_...` でなくなるだけで、使い心地が大きく変わります。

### 5.3 候補の理由を具体的に出す

- 今の状態: 「文字列を参照 · 文字列を参照」。同じ言葉が 2 回出て、どの文字列かも分かりません。
- 原因: `js/ui/panels/investigation.js:192` が、先頭 2 つの理由の**種類**だけを出しています。`reasons[].detail`（中身）は使っていません。
- 提案:
  - 同じ種類の理由は 1 つにまとめます。
  - 中身を出します。例: 「`"hp_max"` を参照」「`-[Player damage:]` から呼ばれる」。
  - 「最も強い答え」の欄に、目的の名前（「HP・体力」）ではなく、1 位の候補とその一番強い理由を出します。

### 5.4 候補を開いたら、読みやすい表示を先に出す

- 今の状態: 候補を開くと、疑似 C のタブが出ます。中身は WASM の「レジスタをそのまま C にした形」で、状態機械（`while (__hex_state) switch`）になることもあります。画面にも「簡易版の逆コンパイラの結果です」と出ています。
- 提案:
  - 目的の検索から来たときは、まず「この関数が HP をどう扱うか」の要約を出します。例: 「`[x19+0x48]` から 8 バイト読み、引いて、書き戻す」。今ある `narrate`、`fields`、`pinpoint` で作れます。
  - 疑似 C では、該当する行を強調します。
  - 読みやすくする本当の解決は、前回のレビュー（`reports/reviews/arm64-wasm-20261128/`）の 8 章です。

### 5.5 検索を「関係の強い順」にする

- 今の状態: 「HP」で探すと、部分一致で 894 件がアドレス順に出ます。`flushPlayer` も当たります。検索の対象も関数だけです。
- 提案:
  1. 単語の境目での一致（`HP`、`Hp`、`hp_`、`_hp`、`kHP`）を上にします。
  2. 関数、文字列、クラス、フィールドをまとめて出します。
  3. 先頭に「目的として調べる: HP・体力」の行を出します。今は目的の検索と普通の検索が分かれていて、つながっていません。

### 5.6 内部のコードを、人の言葉にする

画面にそのまま出ている内部のコードの例:
- `result-limit・function-discovery-incomplete`（HP の結果の上）
- `evidence-store-unavailable`（根拠タブ）
- `analysis-query-binary-unbound`（再読み込みの後）

提案:
- 人の言葉にします。例: 「関数をまだ全部は見つけていません。あと 2 分で全部見つかります」。
- 次にできることのボタン（「続きを調べる」など）を付けます。
- コードは「くわしい情報」の中に入れます。

### 5.7 そのほか、小さい改善

- 関数の「基本情報」で、27 命令の関数が「ブロック数 0」と出ます。数え終わっていないなら「計算中」と出します。
- 「解析状態: 可能性が高い / 一部のみ」の 2 つのラベルは、意味がぶつかって見えます。どちらか 1 つにします。
- 再読み込みすると、ファイルを選ぶ前に前の関数の画面が出て、エラーになります。再読み込みの後は、「前回のファイルを開く」の案内を出します。
- 開いた直後の画面は `__text` の先頭です。代わりに、アプリの地図（主なクラス、目的のボタン、よく呼ばれる関数）を最初に出すと、次に何をするかが分かります。

### 5.8 「概要」が終わらない原因

- 「概要」は、19 個の目的（HP、攻撃力、コイン、ガチャ…）をまとめてファイル全体で調べます。そのあと、各目的の上位の候補を命令まで深く確かめます（pinpoint、最大 360 関数）。結果として、アプリ全体の地図（目的ごとの答え、候補、根拠、未確認の点）を作ります。
- Node で同じ処理を動かして測りました（`investigationServiceFor(app).overview()`）:
  - 文字列、値のふるまい、呼び出しの索引、名前の認識（3.5 秒）、19 個の目的の順位付け（7 秒）: **ここまでで 35 秒**。
  - そのあと「pinpoint 0/19」（最初の目的の深い確認）に入ると、**終わりません**。2 分以上、どのワーカー呼び出しも返りません。メインスレッドのタイマーも動きません。
- V8 のプロファイルで、いちばん時間を使っているのは `exactLegacyConstant`（`js/ir-core.js:1239`）でした。
- 原因:
  - この関数は、値が定数かを、式をさかのぼって調べます。同じ部分の式を何度も計算し直します（結果を覚えておく仕組み＝メモ化がありません）。
  - 式は木ではなく、部分を共有するグラフ（DAG）です。そのため、深さ 128 までの再帰で、計算の量が指数関数的に増えます。
  - しかも `propagateExactLegacyConstants` が、関数の中のすべての値について、これを呼びます。
- これは古い JS の IR（`ir-core.js`）の道で、メインスレッドで動きます。そのため、画面が固まり、キャンセルも効きません。
- 直し方:
  1. `propagateExactLegacyConstants` の 1 回の呼び出しの中で、`value.id` ごとの結果を `Map` に覚えます。
  2. pinpoint を Worker で動かします。
  3. 関数ごとに時間の上限を付けます。上限を超えたら、その関数は「未確認」にして先へ進みます。

## 7. 測り方の限界

- 試したのは 1 つのバイナリ（TsumTsum）だけです。Unity（IL2CPP）のゲームでは試していません。
- 画面は PC の大きさ（1366×900）だけで試しました。iPad の大きさとタッチ操作では試していません。
- 「AI に聞く」と Jev は試していません。外部へデータを送るためです。
- 時間は、このコンテナ（4 CPU）での値です。iPad の Safari では違います。
