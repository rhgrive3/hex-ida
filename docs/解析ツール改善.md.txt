## エグゼクティブ判定と Research Freeze Point

### 総合判定

現行 Hex の最も重要な強みは、単純な「機能数」ではなく、**semantic truth の所有権、unknown/partial の保守性、stable identity/provenance、deterministic budget/cancellation、hard/soft type evidence の分離、EvidenceGraph を中心にした query/UI/AI 境界**を既に設計原則として持っていることである。`docs/flash.md` 自体も `MachineEffects → Semantic IR → CFG → SSA → MemorySSA → alias / points-to / summaries → type/value facts → decompiler projection → query/UI/AI` を single-truth chain とし、false `NoAlias`、false `MustAlias`、false exact indirect target、false exact type、semantic mismatch、stale publication をゼロにする release invariant を明示している。これは「もっと賢く見せる」競合追従ではなく、**証拠が揃った時だけ精度を上げられる構造**として非常に価値が高い。fileciteturn41file0L1-L2

一方、最も大きな残差は、現在の保守性が精度に変換され切っていない境界に集中している。特に、現行 local points-to は **memory-loaded pointer と call-return pointer を明示的に unresolved boundary としている**。この選択自体は正しく、unsound な推測を避けているが、既に存在する MemorySSA と interprocedural summaries を用いてこの境界を安全に閉じる余地が大きい。fileciteturn30file0L1-L2

第二の大きな残差は C-ME の「coverage declaration」と「独立 semantic oracle proof」の違いである。Hex 側の profile/support declarations は x86/x64/ARM64/RV64 の広い表面を宣言しているが、外部の `rax` が示す real hardware/KVM/QEMU/ASL differential methodology は、**実装とは独立した誤り検出能力**を提供する。`rax` は x86-64 を KVM/real hardware、AArch64 を hardware/QEMU+ASL、Hexagon/RISC-V を QEMU と同一初期状態から比較し、x87、AVX-512/APX、SVE/SVE2、RVV まで対象にしている。Hex が採るべきなのはこの runtime architecture ではなく、**verification method** である。citeturn22search12

第三は C4。Ghidra の公開 decompiler source が示す最大の教訓は「どの simplification rule があるか」以上に、**pass ordering、fixed-point、restart、heritage/dead-code ordering、invalidation、non-convergence の扱いが correctness architecture そのもの**だという点である。Ghidra は Actions を変化がなくなるまで反復でき、restart を bounded にし、type inference にも明示的な pass limit を持たせる。また heritage が十分に進むまでは dead-code を許可しない。Hex の decompiler を強くするには、競合の最終 pseudocode を真似るより、この lifecycle discipline を Canonical Semantic IR / MemorySSA の上に取り込む方が leverage が大きい。citeturn10view0turn11view1turn11view2turn11view3

第四は symbolic。現行 Hex には browser-safe な真正の exact Bool/BV finite-domain solver があり、SAT model を Hex 自身で再評価し、unsupported/resource limit を proof に昇格させない。しかし default `maxBvWidth = 8` であり、full-width binary reasoning の主 solver にはならない。fileciteturn47file0L1-L2 Z3 の公式 WebAssembly package は存在するものの、公式ドキュメント上 threads と `SharedArrayBuffer` を要求し、browser 側には cross-origin isolation が必要であるため、「WASM があるから現在の iPad/userscript にそのまま入る」という前提は成立しない。citeturn17search2turn18search1turn19search0

第五は Stage 2。runtime、managed、native rebuild、persistence、extensions、collaboration には provider/adapter architecture が既に存在する。したがって次の課題は provider を増やすことではなく、**provider presence ≠ proven capability** を守りながら、vertical workflows、identity binding、independent reparse、real-device/browser proof を閉じることにある。現行 `js/runtime/**` には debugger/emulator/instrumentation/evidence bridge が既に存在する。fileciteturn53file0L1-L2

### 現行 Hex の重要な設計上の優位

**Unknown-call conservatism は維持すべきである。** 現行 interprocedural solver は missing/stale/incomplete callee を「no effect」と扱わず broad unknown effect にし、non-exhaustive indirect target set は known candidates に unknown-call effect を追加する。recursive SCC が budget 内で収束しなければ optimistic intermediate を publish せず conservative incomplete summary に置き換える。これは競合から置換すべき弱点ではなく、**外部アルゴリズムを導入する時に絶対に壊してはならない Hex advantage** である。fileciteturn32file0L1-L2

**Type ambiguity の扱いも同様である。** Hex は contradictory hard constraints に「70% の型」を選ばず selection を withheld し、soft evidence が hard contradiction を消せない。これは Retypd/Oxidizer 系のより広い inference を受け入れるための良い authority shell であり、新しい type engine で置換するより、現在の `TypeConstraintGraph` に新しい evidence producers を接続すべきである。fileciteturn52file0L1-L10

**MemorySSA も作り直すべきではない。** current implementation は calls/intrinsics、unknown clobber、may/must/unknown relation、access sequencing を一つの canonical memory truth に統合している。C1/C2 precision work はこのエンジンを再利用し、二つ目の reaching-def/memory model を作らないのが正解である。fileciteturn36file0L1-L2

## 外部実装研究と source registry

### IDA / Hex-Rays の lawful public surface

`HexRaysSA/ida-sdk` は公開 SDK として利用できるが、これから proprietary decompiler core の内部アルゴリズムを推論してはいけない。今回 source-reviewed と扱ったのは public SDK/API、public repositories、lawful plugins、independent IDB parsers 等だけである。`ida-sdk` は MIT の public source である。citeturn9search0turn9search1

`ida-domain` の重要な lesson は、低レベル API を無秩序に agent に投げるのではなく Functions/Types/Xrefs の domain abstraction を提供する点にある。Hex ではこれを query layer に適用し、AI が rendered text を再解釈するのではなく stable semantic entities を query させるべきである。citeturn9search5

`ida-codemode` から得られる最重要 lesson は、agent/session workspace と database authority を分離することである。persistent REPL/handle は lease-scoped にし、handle ごとの namespace/isolation を持たせ、session state が canonical database semantics そのものにならないようにする。これは Hex の EvidenceGraph と非常に相性がよい。citeturn2search1

recursive discovery では Hex-Rays 公開 plugin `goomba` も重要だった。これは MBA/opaque-predicate simplification に Z3 を使って soundness を検証し、non-linear case では fingerprint oracle を使用する。Hex にとっての lesson は「MBA simplifier を付ける」ことではなく、**deobfuscation rewrite は semantic-equivalence proof が通った時だけ canonical projection に昇格させる**ことである。citeturn20search7

IDA agent ecosystem の `IDASQL` や `idac` も、queryability、multiple database handles、headless/GUI session routing に有用な UX lesson を示す。一方、Hex では read/write agent surface が analysis authority を迂回して canonical facts を書き換える設計は採用すべきでない。citeturn20search5turn20search11

**禁止境界:** proprietary Hex-Rays core の hidden SSA/type algorithms は **NO STRONG PUBLIC SOURCE FOUND** であり、推測・byte-for-byte reconstruction の対象外とした。leaked/cracked/pirated source/binary は一切使用していない。

### Ghidra — primary open decompiler reference

Ghidra の最大価値は個々の peephole rule ではなく、公開された C++ decompiler が **phase lifecycle をコードで証明している**ことにある。

`Action::perform` は repeat flag と change count を使って収束まで反復でき、`ActionRestartGroup` は restart を bounded にする。citeturn10view0 `coreaction.cc` の universal action sequence は heritage、parameter recovery、local restriction、dead code、dynamic mapping、spacebase recovery、nonzero mask、type inference、varnode restructuring、repeat rule pools の順序を明示する。type inference 自体にも bounded pass limit があり、settle しない場合は warning/state を残す。citeturn11view2turn11view3

`heritage.cc` では address-space ごとの heritage/deadcode delay を持ち、SSA/heritage が十分に閉じる前に dead-state elimination を始めない。clear/restart 時には多数の maps/caches/pass state をまとめて invalidation する。Hex にとってこれは **premature DCE と stale analysis cache を structural invariant で防止せよ**という lesson である。citeturn11view1

2026 年の Ghidra failure history はこの教訓をさらに強くする。Sleigh `PcodeCacher` では vector reallocation 後に raw pointer を使ったため use-after-free、`HighVariable::merge` では削除された variable が intersection cache に残って use-after-free が起きた。前者は stable reference/ID、後者は atomic cache invalidation の重要性を直接示す。citeturn22search5turn22search6

さらに Mach-O loader は attacker-controlled `ncmds` をそのまま巨大 allocation に使う resource-consumption bug を持ち、ELF GNU hash parser は unbounded loop、out-of-range zero provider、cancellation disabled の組合せで永久 hang を起こした。Hex の browser/iPad environment ではこの種の bug は desktop よりさらに重大であり、**file-bound validation、allocation budgets、iteration cap、always-cancellable parsing** を format lane の hard invariant にするべきである。citeturn22search4turn22search8

`udiv128` simplifier でも fixed-size temporary の境界ミスが compiler-idiom simplification から reachable だった。Hex の JavaScript は同じ memory corruption class を持たないとしても、bit-width、BigInt→bitvector normalization、index bounds を simplifier property tests で独立に証明する必要がある。citeturn22search7

なお GitHub release widget の取得結果は 2026-05-13 の `Ghidra 12.1` を “Latest” としていたが、一次情報の advisory/issue は 12.1.1/12.1.2 の存在を明確に示している。したがって crawler の “Latest” 表示は stale と判断し、本報告では version marketing ではなく source mechanism/advisory を authority とした。citeturn22search0turn22search8turn22search9

### Binary Ninja / WARP

Binary Ninja proprietary core は source-reviewed としていない。一方 open `binaryninja-api` が公開する MLIL/SSA API からは、memory SSA version、memory φ、SSA loads/stores/calls、aliased variables、IL-to-IL mappings、use-def exposure が API contract の一部であることが観測できる。Hex にとっての opportunity は「BN の IL をコピーする」ことではなく、**canonical memory/value truth を result navigation/API から直接辿れること**である。citeturn3search2turn3search4

WARP は recognition lane で特に重要である。function GUID を basic-block GUID 群から構築し、instruction normalization では relocation-sensitive bytes を扱い、NOP/self-move 相当を正規化する。より重要なのは **一つの GUID に複数候補があれば collision を削除せず保持し、caller/callee/adjacency 等の constraints で絞る**設計である。firmware の relocation 情報不足は明確な failure mode になる。citeturn22search14turn3search0

Hex はこれを `signature/knowledge/diff` に取り込む際、fingerprint match を exact semantic fact とせず、候補集合、algorithm version、normalization version、constraint evidence、collision cardinality を保存すべきである。

### angr / Triton / Retypd / other decompilers

angr AIL の有用な lesson は optimized graph だけを残さず、unoptimized graph と instruction mapping を保持することである。これにより decompiler projection が canonical low-level evidence へ戻れる。Hex の EvidenceGraph と同じ方向性であり、C4 では raw→optimized→rendered mapping を transform record として保持すべきである。citeturn4search9

Claripy は solver abstraction、AST translation、backend caching、timeout/interrupt、model handling を solver-independent layer に置く。Hex の現行 `solver/backend/session/worker` 分離は方向として正しく、置き換えではなく capability breadth を足すべきである。citeturn4search2

Triton の symbolic memory では concrete/QF_BV memory が scale のための default であり、symbolic pointer を必要とする時に array/QF_ABV model を使う選択肢がある。この二段階性は browser Hex に適している。すべての load/store を最初から SMT Array にするのではなく、MemorySSA/concrete regions を first tier、必要な query だけ array backend に昇格するのがよい。citeturn5search1turn5search8

Retypd の recursive types/subtyping は modern binary type recovery の強い研究基盤だが、reference implementation は GPLv3 である。したがって Hex では paper-level algorithm/invariants を **CLEAN-ROOM-ONLY** とし、現行 `TypeConstraintGraph` の hard/soft authority model の下に independently implement するのが適切である。citeturn5search2turn5search3

`gtirb-ddisasm-retypd` の failure/limitation からは generic arithmetic alone では signedness を誤り得ること、FP/vector sinks、globals、parameter-count discrepancies が type quality を落とすことが分かる。したがって Hex は opcode/ABI-specific hard evidence と generic structural constraints を混同すべきでない。citeturn5search0

Rust 向け Oxidizer は compiler-version-sensitive recovery と複数 possible types を保持する。Hex の既存 ambiguity model と相性が良い。language recovery provider は「最も plausible な Rust type 一個」を hard fact にするのではなく、toolchain/version evidence と alternatives を TypeConstraintGraph に供給すべきである。citeturn4search1turn4search0

decompilation structuring では dewolf/DREAM 系が irreducible CFG/loop/condition restructuring の重要な研究源だが、dewolf は LGPL 系であるため **CLEAN-ROOM-ONLY**。最終 pseudocode の美観より equivalence と raw fallback を優先する。citeturn6search0turn6search6

### Machine semantics、runtime、formats、languages、recognition

`rax` と Rizin `rz-tracetest` は独立 differential semantics の最も直接的な source class である。Remill の formal-validation history でも `xadd` 等の semantics discrepancies が見つかっており、「成熟した semantics library だから正しい」とは言えない。複数 oracle が disagree した時は spec/hardware を上位 authority とし、maskable undefined state を比較から除外する仕組みが必要である。citeturn22search12turn7search5turn7search7

Miasm の symbolic overlapping-memory failure では signed pointer difference の扱いから異常に大きい overlap width が生じた例があり、Hex C2/C-SYM には **modular-width checked arithmetic と impossible overlap invariant** が必要である。citeturn7search9

Frida Gum の Stalker は block の shadow copy/dynamic recompilation、call/block/instruction event streams、cached code、self-modifying-code trust threshold を持つ。Hex が採るべきなのはその desktop-native core ではなく、**runtime trace event を static bytes/hash + module/build identity + generation に bind し、stale trace を canonical fact にしない**点である。runtime provider は `REMOTE/BRIDGE-OPTIONAL` とし、browser は indexing/query/evidence projection を所有する。citeturn8search2turn8search3

Qiling は OS/environment emulation、Unicorn は native execution engine、rr は Linux record/replay として強力だが、これらを mandatory iPad architecture にするのは不適切である。build-time oracle または optional remote provider として価値がある。citeturn8search0turn8search1turn8search13

LIEF は ELF/PE/Mach-O の parse/modify/build、DWARF/PDB、ObjC、dyld-cache 関連を持つ permissive reference であり、integration branch が既にこの lane を進めている以上、推奨は「LIEF を導入せよ」ではなく **writer-independent validation を追加せよ**である。citeturn13search0turn13search2

Apple では dyld cache header が code signature、local symbols、UUID、subcache/patch-related metadata を含み、Mach-O chained fixups/signature reconstruction が単純な section rewrite では済まない。citeturn12search2turn13search7 Swift ABI docs は metadata layout の有用な authority だが、一部 nominal-type textual documentation 自身が out-of-date と警告しており、runtime headers は unknown metadata kinds を forward-compatible に扱う必要を示す。したがって Hex の Swift provider は documentation snapshot に固定せず、**compiler/runtime version identity を解析結果に記録する**べきである。citeturn13search1turn13search3

GoReSym は Go runtime/compiler の version-specific knowledge を利用し、stripped/malformed/UPX/split ranges といった実際の binary conditions を扱う。Hex では同じ考えを採り、まず toolchain/build fingerprint を evidence として確立し、その version の `pclntab/moduledata/types` parser を選ぶべきである。citeturn14search0

ILSpy は .NET metadata/PDB/ReadyToRun を含む成熟した managed workflow の reference で、JADX は DEX/APK/AAB/resources/deobfuscation を一つの application workflow として扱い、自身も全入力を完全 decompile できるとは主張していない。Hex の `managedIlspy` / `managedJadx` lane は既にあるので、次に測るべきは VM opcode count ではなく **metadata→types→exceptions→resources→source navigation の vertical maturity** である。citeturn14search4turn14search7

BinDiff は structural matching cascade、BinExport は IDA/BN/Ghidra を跨ぐ interchange surface として有用である。Hex では BinExport を optional oracle/interchange として使う余地があるが、canonical entity schema を BinExport に合わせて置換すべきではない。citeturn15search4turn15search6

Diaphora の長期 history では unreliable heuristics の移動/廃止が生じている。これは recognizer heuristic を「永続的な truth rule」にしない理由になる。algorithm version、feature set、confidence/evidence、collision set を保存する必要がある。citeturn15search5

PatternLanguage/ImHex、YARA-X、capa の lesson は pattern/rule ecosystem を parser/type authority と混同しないことにある。YARA-X のような bounded rule engine と versioned package model は useful だが、match は `knowledge evidence` であり semantic truth ではない。citeturn16search1turn16search2turn15search3

## ベンチマーク、data/corpus、license、iPad viability

### Ground-truth methodology

競合出力を ground truth にしてはいけない。この研究で推奨する benchmark fixture pipeline は次である。

`source-level truth → pinned compiler/toolchain/flags → one compiled artifact → debug oracle view + stripped twin → Hex analysis → independent metrics`

重要なのは **debug binary と stripped binary を別々に compile しない**ことである。同じ code bytes を持つ twin を作ることにより compiler/code-layout drift を elimination できる。debug metadata は answer generator ではなく identity-matched oracle としてのみ使用する。現行 Hex type model も identity-matched debug source だけを hard constraint origin と認める設計になっている。fileciteturn51file0L1-L10

Competitor execution は lawful license がある環境でのみ secondary differential evidence とする。IDA/BN を実行できない環境ではその metric は **UNMEASURED** とし、公開 benchmark の historical number を現在の Hex victory score に流用しない。

**Correctness と readability は別計測する。** DecompileBench のような recompilation/coverage と readability を分ける方向は正しいが、LLM readability score は semantic truth ではない。citeturn6search3

推奨 measurement contract:

| Dimension | Ground truth | Critical negative metric |
|---|---|---|
| instruction semantics | ISA spec / hardware/reference execution | mismatched defined bit/register/memory |
| function starts/extents | source/debug symbols from same artifact + hand fixtures | false function start/extent |
| CFG | source-labeled fixtures + exact decoded control flow | false/missing edge |
| indirect targets | fixture-defined exhaustive target set | false exact target |
| alias | object/layout construction | false MustAlias / false NoAlias |
| MemorySSA | deterministic stores/loads + byte layout | wrong reaching definition |
| prototypes | compiler ABI/debug same artifact | wrong hard ABI claim |
| aggregates | source layouts/debug | false exact field/type |
| decompiler semantics | execution/property equivalence | semantic mismatch |
| readability | structural metrics/human rubric separate | avoidable goto/temp/cast only after semantic pass |
| performance | fixed device/browser/toolchain | TTFUA, active-function latency, peak memory |
| lifecycle | synthetic cancellation/stale snapshot | stale publication, cancellation latency |

### Corpus plan

**MachineEffects corpus:** generated per ISA/profile with instruction bytes, initial registers/vector/flags/memory, defined-result mask, expected exception/trap, oracle ID/version, CPU feature set。x86 profiles must explicitly cover x87/SSE/AVX/AVX-512/APX/system instructions; ARM64 includes FP/SIMD/SVE/PAC-relevant semantics; RISC-V profile must name exact extensions rather than “RV64” generically。rax demonstrates that this breadth is testable with independent execution.citeturn22search12

**Alias corpus:** same/different stack object, global/TLS, allocation sites, escaped/non-escaped objects, overlapping/disjoint fields, φ same/different roots, loop-carried pointers, pointer store/load, direct/recursive pointer returns, exhaustive/non-exhaustive indirect calls, unknown call/store barriers。`docs/flash.md` already enumerates much of this, so the delta is implementation oracle linkage rather than a second corpus.fileciteturn41file0L1-L2

**ABI/type corpus:** SysV x86-64, Win64, AAPCS64, RV64 ABI; integer/FP/vector class, sret, small struct return, HFA/HVA, varargs, tail calls/thunks, callbacks/function pointers; contradictory debug/runtime metadata。

**Decompiler corpus:** reducible/irreducible CFGs, nested loops/switches, break/continue, tail calls, exceptions, compiler state machines, flattening, MBA, aggregate loads/stores, vector idioms。semantic correctness must be checked before goto/temp/cast counts。

**Format malformed corpus:** attacker-controlled counts, truncated tables, cyclic/unterminated tables, integer overflow, overlapping segments, huge allocation claims, bad relocations, bad unwind, invalid code signatures。2026 Ghidra Mach-O/ELF failures make this a P0 safety corpus rather than optional fuzzing。citeturn22search4turn22search8

**Runtime corpus:** ASLR、module reload、same VA/new binary generation、self-modifying/JIT、dropped events、trace overflow、cancellation、remote disconnect、thread race。

**Managed corpus:** versions of .NET/CIL/ReadyToRun/PDB、DEX/APK/AAB/resources、Go toolchains、Rust toolchains、Swift ABI versions、ObjC runtime layouts。opcode coverage と application workflow score は別 denominator にする。

### Do Not Adopt

**Full-SMT-everywhere を採らない。** Binary analysis の大半を最初から SMT Array + full-width solver に流すと iPad memory/startup/cancellation が悪化する。MemorySSA、cheap value domain、concrete symbolic memory を first tier にする。

**Z3-WASM を「WASM だから browser-native」と呼ばない。** 公式 requirement は threads/SAB/cross-origin isolation を含む。first-party isolated deployment の実測が通るまでは optional backend である。citeturn18search1turn19search0

**Ghidra の architecture を wholesale port しない。** Action lifecycle、ordering、invalidation の lesson は採るが、Hex の canonical pipeline/EvidenceGraph を置き換える必要はない。

**IDA/BN proprietary internals を推論して clone しない。** public SDK/API/behavior 以外は authority がない。

**Pretty pseudocode を correctness より上に置かない。** irreducible CFG には goto/raw fallback が正しい場合がある。

**Signature collision を削除しない。** WARP が複数候補を保持するのは重要な safety property である。citeturn22search14

**Symbol/function/root names を hard semantic proof にしない。** 特に PR #1413 の root-key spelling を利用するように見える path は exact NoAlias publication 前に binary provenance を要求すべきである。fileciteturn48file0L1-L2

**Dynamic trace を static truth の上書きに使わない。** Runtime state は exact binary/module generation に紐付いた evidence である。

**Writer-only rebuild validation を採らない。** 同じ serialization logic が作った object を同じ assumptions で読み返しただけでは独立性が弱い。

**Copyleft source structure の直接移植をしない。** Retypd/dewolf/Miasm/Diaphora/PatternLanguage 等は paper/behavior/invariants を clean-room で使う。

**Community data を implementation license だけで bundle しない。** signatures/rules/patterns の provenance は別審査。

**Provider presence を maturity と呼ばない。** Frida/ILSpy/JADX/LIEF adapter が存在しても、real-device/real-file/vertical workflow proof がなければ mature capability ではない。

### Final technical verdict

Hex が最も大きく勝てる経路は、「他ツールが持つ機能を全部追加する」ことではない。

勝ち筋は、

**independent MachineEffects proof**  
→ **MemorySSA を使った sound pointer/value precision**  
→ **ambiguity-preserving ABI/type recovery**  
→ **bounded/invalidation-safe decompiler fixed points**  
→ **solver/runtime/managed/native providers を canonical evidence に正しく接続**  
→ **same-binary ground truth で競争結果を再現可能にする**

という既存 architecture の延長にある。

特に重要なのは、current Hex の unknown/partial discipline を弱めずに exact recall を上げることである。`unresolved-load` や `unresolved-call` は失敗ではなく、現状の proof boundary を正直に示す安全機構である。そこを MemorySSA exact reaching store と complete interprocedural summary からだけ閉じれば、単一改善が alias → values → types → aggregates → decompiler → query → AI explanations まで波及する。fileciteturn30file0L1-L2 fileciteturn32file0L1-L2

同様に、Ghidra から最も学ぶべきものは最終 pseudocode の形ではなく、pass ordering、fixed-point、restart、invalidation、resource limits、malformed-input history である。2026 年の公開 security/failure history は、成熟した decompiler でも stale references、unbounded parsing、uncancellable loops、simplifier bounds bugs が長く潜伏し得ることを示した。citeturn22search4turn22search5turn22search6turn22search7turn22search8

そして browser/iPad advantage は捨てる必要がない。`rax`、QEMU、rr、Frida、Qiling 等の desktop-native 技術は **offline oracle / optional bridge** として取り込めばよく、production truth engine を native desktop architecture に移す理由にはならない。逆に current Hex の deterministic browser analysis、small exact solver floor、EvidenceGraph、stable provenance を保ったまま、重い solver/runtime/oracle を外側に配置する方が competitive differentiation になる。

最終的に「Hex が major RE tools より強い」と主張できるのは、競合と似た UI や prettier pseudocode を得た時ではなく、**independent ground truth 上で false exactness を増やさず precision/coverage/workflow breadth を上げ、その結果が exact identities・reproducible corpus・actual iPad/browser constraints の下で再現された時**である。
